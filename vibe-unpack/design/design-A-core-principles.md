# vibe-unpack 设计定义（阶段 A）

**版本**: v0.1  
**日期**: 2026-07-29  
**状态**: 草案 - 核心原则与边界定义

---

## 1. 核心定位

**vibe-unpack** 是一个**独立的、纯净的需求解包器**（Demand Unpacker）。

它的唯一职责是：
> 把普通人脑中模糊的「感觉 / 场景 / 情绪」通过结构化追问，逐步展开成**清晰、闭合、可被后续流程消费**的需求图谱与规格。

**它不是**：
- 代码生成器
- 技术栈推荐器
- 技能匹配器 / 筛选器
- 业务验证器
- MVP 构建指导器

这些功能应该由**其他独立 skill** 负责（例如未来的 `skill-recommend`、`validate-idea`、`processize`、`brainstorming` 等）。

**它扮演的角色**：懂技术的「需求雕塑师」 + 「产品经理」。

---

## 2. 核心原则（必须严格遵守）

1. **模糊输入是常态，不是异常**
   - 用户说“我想做一个像小红书但更简单的” 是合法输入。
   - 永远不要要求用户“先把需求说清楚”。

2. **当前 workaround 是最重要的支点**
   - 必须先彻底搞清楚用户**现在**是怎么解决这个问题的（工具 + 具体步骤）。
   - 所有后续挖掘都以此为锚点。

3. **痛点必须具体到“崩溃时刻”**
   - 禁止使用“太麻烦”“不够好”这类抽象描述。
   - 必须追问：过去1个月哪3个瞬间让你特别想砸东西？

4. **约束比功能更重要**
   - 普通人最缺的是**负向知识**（这个不能选，因为...）。
   - 必须主动挖掘：时间预算、学习意愿、维护能力、是否有会编程的朋友、3个月后可能不管等。

5. **隐性假设必须被挖出来**
   - 用户往往不知道自己做了哪些危险假设。
   - 必须系统性挑战“数据不能丢”“必须多人用”“要像XXX一样”等。

6. **成功/失败定义是终止条件**
   - 必须明确：3个月后什么算“值了”？什么算“白做了”？

7. **分支与权衡必须记录**
   - 每个重要决策点都要记录：有哪些选项？为什么选这个？放弃了什么？代价是什么？
   - 人类用户需要看到“为什么走到这里”。

8. **输出必须双格式**
   - **人类优先**：可视化知识图谱（分支、判断、优缺点一目了然）
   - **AI 智能体优先**：结构化 Markdown（可被后续 skill 可靠解析）

---

## 3. 严格边界（In / Out of Scope）

### In Scope（必须做）

- 现状映射（当前 workaround 的完整流程）
- 痛点图谱（具体崩溃时刻 + 频率 + 严重程度）
- 硬约束发现（时间、金钱、能力、维护、部署、离线等）
- 隐性假设与风险暴露
- 成功/失败定义
- 关键分支决策记录（带权衡）
- 输出双格式制品（Markdown + Graph）
- 产生可执行的“下一步验证动作”

### Out of Scope（坚决不做）

- 推荐任何具体技术栈、框架、数据库、部署方式
- 匹配、推荐、筛选任何 skill（本地或外部）
- 写代码、生成 skeleton、写计划
- 进行商业验证（“会不会有人买”）
- 设计 UI/交互细节
- 假设用户有技术背景或有会编程的朋友
- 产出“功能列表”或“用户故事”

**违反边界的惩罚**：如果输出中出现了具体技术推荐或技能推荐，必须被视为错误。

## 4. 输出物定义（Output Contract）

### 4.1 结构化 Markdown 报告

**推荐文件名**：`demand-spec.md`（放在用户项目根目录或 `docs/requirements/` 下）

**必须包含的章节**（顺序固定，便于 AI 解析）：

```markdown
# 需求规格书：{一句话核心需求}

## 0. 执行摘要
（1-2 句话：这个用户真正想要的本质是什么？最核心的约束是什么？）

## 1. 当前状态（Current Workaround）
- 用户现在使用的工具/方法
- 完整操作步骤（越具体越好）
- 每次使用大概花费的时间/心智负担

## 2. 痛点地图（Pain Map）
每个痛点必须包含：
- 具体场景描述（“上周三晚上10点...”）
- 崩溃时刻（用户描述的原话）
- 频率
- 严重程度（1-5）
- 为什么现在必须解决

## 3. 约束账本（Constraint Ledger）
分类列出：
- **硬时间约束**
- **能力与维护约束**
- **数据与隐私约束**
- **部署与可用性约束**
- **预算约束**
每个约束必须标注：证据来源 + 后果（如果违反会怎样）

## 4. 隐性假设与风险（Assumptions & Risks）
- 列出用户自己没意识到的假设
- 每个假设标注：风险等级 + 验证方式

## 5. 成功与失败定义（Success/Failure Criteria）
- 3个月后的“成功”样子（可观测、可测量）
- 3个月后的“失败”样子
- 关键里程碑（如果有）

## 6. 实现路径建议（Implementation Path）—— 高层级
**仅限过程与策略层，不涉及具体技术**：
- 推荐的整体策略（例如：先 processize 3个月 / 直接最小可行代码 / 纯手动等）
- 必须先验证的事项（具体到“找哪类人验证什么”）
- 范围裁剪建议（什么可以砍掉）
- 风险缓解措施

## 7. 决策日志（Decision Log）
对每个重要分支点记录：
- 决策问题
- 备选选项（至少2个）
- 选择结果
- 选择依据
- 放弃的代价 / 保留的风险
- 证据来源

## 8. 下一步行动（Immediate Next Steps）
必须是**可立即执行的**具体动作（最多5条）：
- 找谁聊
- 记录什么
- 手动验证什么
- 等等
```

### 4.2 知识图谱（Knowledge Graph）

**目标受众**：人类用户（直观看到展开过程、分支、权衡）

**推荐格式**：
- JSON 结构（`demand-graph.json`），可被程序消费
- 同时提供可视化表示（Mermaid / 简单 HTML / Obsidian canvas 格式等）

**节点类型（初步）**：

| 类型 | 含义 | 示例 |
|------|------|------|
| `Anchor` | 初始支点（用户原话或当前 workaround） | “我现在用手机备忘录记孩子日常” |
| `PainPoint` | 具体痛点 | “每次想找3个月前的记录要翻好久” |
| `Constraint` | 硬约束 | “我不会编程，朋友也不会” |
| `Assumption` | 隐性假设 | “数据一定不能丢” |
| `Alternative` | 已有替代方案 | “我试过小红书，但太复杂” |
| `SuccessCriterion` | 成功标准 | “3个月后我还能自己维护” |
| `DecisionPoint` | 决策节点 | “要不要支持多人协作？” |
| `Risk` | 风险 | “如果3个月后我不管了，程序会怎样？” |

**边类型（初步）**：

- `anchors_from` / `expands_to`
- `causes` / `mitigates`
- `constrains`
- `contradicts`
- `supports`
- `prunes` （因为约束而被砍掉）
- `chosen_over` （决策时被选中的选项）
- `leads_to_risk`

**图谱必须表达的关键信息**（对人类重要）：
- 从模糊起点到结构化终点的**展开路径**
- 每个 `DecisionPoint` 的**分支选项 + 选择依据 + 权衡**
- 哪些路径因为**约束**被剪掉（pruned）
- 哪些痛点至今仍未被任何方案覆盖

## 5. 成功标准（如何判断这个 skill 做得好）

一个好的 `vibe-unpack` 输出应该让后续的 AI 或人类看到后能说：

> “现在我终于知道这个项目真正要解决什么、不能做什么、为什么这样选了。”

具体可观测指标：
- 用户的原话被**大幅重构**，但核心意图被保留
- 至少发现 3 个用户自己没意识到的约束或假设
- 决策日志中至少有 2-3 个有真实权衡的分支
- 下一步行动具体到“下周二之前找 XX 做 YY”
- 人类用户看图谱后能**自己解释**为什么走到这个路径

## 6. 与其他 skill 的关系（接力图）

```
模糊想法
   ↓
vibe-unpack（本 skill）
   ↓ 输出：demand-spec.md + demand-graph.json
   ↓
可选：validate-idea（值得做吗？）
   ↓
可选：processize（先手动验证）
   ↓
brainstorming / vibe（准备构建）
   ↓
实施
```

**vibe-unpack 绝不越过** `validate-idea` 或 `brainstorming` 去做它们的事。

## 7. 后续阶段计划（A 完成后的顺序）

1. **阶段 B**：详细设计知识图谱的节点/关系 schema + 追问维度（支点展开的 6 个方向）+ 闭合条件
2. **阶段 C**：设计 4-6 个压力场景（典型普通人输入），用于后续 TDD 式验证
3. 编写 SKILL.md（基于 A+B+C）
4. 实现必要的工具/模板（如果需要）
5. 压力测试 + 迭代
