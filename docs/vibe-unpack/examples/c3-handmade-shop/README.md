# 演示范例：C3 - 手作店网站（被频繁打扰才是核心问题）

## 场景背景

用户做手作（针织、陶艺），想做一个"清爽的网站"把作品放上去，别人能看到、能联系。

**关键洞见**：用户嘴上说要"网站门面"，但**每天被 5-10 个重复私信打扰**才是真正的最大痛点。建网站本身不能减少打扰。

这个例子展示了 `vibe-unpack` 如何：
- 把用户真正的痛点（客服）从表层需求（网站）中挖出来
- 挑战"先建站"的默认顺序
- 处理"嘴上说不管但实际上要持续更新"的内在矛盾

---

## 初始输入

> 给我的小手作店做一个网站。把作品放上去，别人能看到、能联系我买。不要太花哨，就清爽一点就行。

---

## 展开后的真相

通过追问发现：

- **每天 5-10 个私信**问价格、问能不能定制
- 小红书内容容易被冲掉，缺少稳定门面
- 交易流程混乱（忘发货、讨价还价、客服乱）
- **完全不会前端、设计、开发**
- 预算 500-1000 元一次性，不愿意订阅
- **实际上每月都要上新作品**（用户嘴上说"放上去就不管"，但实际要持续更新）

**决策点**：
1. 网站是核心还是客服减负是核心？ → **客服减负优先**
2. 网站谁来维护？ → **必须 no-code 模板，用户只填内容**

**推荐路径**：
- **第一阶段（现在）**：把过去 3 个月最常被问的 10 个问题整理成一段自动回复
- **验证 2 周**：看被打扰次数是不是减少了
- 如果还是需要网站，再考虑 no-code 方案

**被剪掉的方案**：
- 自己写代码 / 自己维护（完全不会）
- 月度订阅超过 50 元的方案
- 任何要求用户自己设计 UI 的方案

---

## 产出文件

- `demand-spec.md` — 完整分析（客服减负优先）
- `demand-graph.json` — 知识图（客服痛点如何压倒展示需求）
- `demand-graph.mmd` — 可视化

这个例子是"用户说要什么 ≠ 用户真正需要什么"的典型案例。
