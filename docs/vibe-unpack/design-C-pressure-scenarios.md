# vibe-unpack 压力场景设计（阶段 C）

**版本**: v0.1  
**日期**: 2026-07-29  
**前置**: 已完成阶段 A（核心原则）、阶段 B（图谱 schema + 六大维度）  
**目的**: 为后续 TDD 风格的 skill 开发提供可执行的测试用例  
**状态**: 草案

---

## 1. 压力场景的设计原则

每个场景必须满足以下条件，才能有效测试 `vibe-unpack`：

1. **输入极度模糊**：用户用日常语言描述“感觉/场景/情绪”，几乎不包含技术词汇或结构化需求。
2. **真实性**：来自普通人（非程序员）的真实想法。
3. **多维度陷阱**：容易诱导 AI 犯以下错误：
   - 过早推荐技术栈
   - 直接列功能列表
   - 假设用户有技术背景或“会找人帮忙”
   - 忽略维护/长期性约束
   - 把“像XXX”当成要完整复制
   - 只抓功能不抓约束
4. **有明显支点**：用户当前确实在用某种 workaround（备忘录、Excel、朋友圈、手写等）。
5. **包含隐藏约束**：用户自己可能没意识到，但一旦问出来会大幅改变路径。

## 2. 压力场景清单（共 6 个）

### 场景 C1: “像小红书但更简单” —— 记录孩子日常（经典场景）

**初始用户输入**：
> 我想做一个像小红书但更简单的 App，专门记录我和孩子的日常。就是想把照片、视频、一些小故事存起来，也能偶尔分享给家人看。

**用户真实背景（测试时不提前告诉 AI）**：
- 现在用手机备忘录 + 相册
- 想找旧记录很麻烦
- 奶奶想看就截图发微信
- 用户是全职妈妈，完全不会编程，身边也没有会编程的朋友
- 预算几乎为零
- 可能只用 3-6 个月，之后精力会转移到别的事

**关键测试点**（vibe-unpack 必须覆盖）：
- 彻底挖出当前 workaround（备忘录 + 微信截图）的完整流程
- 发现“不会编程 + 无人可求助”的硬约束
- 挑战“像小红书”的假设，到底要不要“被点赞”“被搜索”“被发现”
- 多人 vs 单人的决策（奶奶要看）
- 3个月后不管了怎么办（数据 + 维护）
- 数据丢失容忍度

**常见 AI 失败模式**：
- 立刻推荐 “用 Flutter / React Native 做个 App”
- 直接开始列功能：发布、点赞、评论、关注...
- 假设用户可以找程序员朋友帮忙
- 完全不问“3个月后你还管不管”

**成功标准**：
- 至少发现 3 个强硬约束
- 至少 1 个 DecisionPoint（多人/单人、公开/私密、本地/云端等）
- 输出中明确指出“当前路径下推荐先 processize，而不是写代码”
- 下一步行动具体到“下周找 2-3 个其他妈妈聊聊她们是怎么记录的”

### 场景 C2: “记账但不要太复杂”

**初始用户输入**：
> 我想做一个记账的 App，就简单的，输入一下花了多少钱、干什么用的就行。不要像那些记账软件那么复杂，我用着烦。

**用户真实背景**：
- 现在用 Excel + 手机备忘录
- 每个月月底对账很痛苦
- 想知道“这个月吃饭花了多少”“给孩子买东西花了多少”
- 用户是 35 岁上班族，Excel 用得还可以，但讨厌分类和打标签
- 手机上不想装太多 App
- 不想手动分类每一笔

**关键测试点**：
- 当前 workaround 的具体痛苦点（月底对账）
- 是否真的需要“App”？Excel 是不是已经够了？
- 自动分类 vs 手动输入的权衡
- 数据需要同步吗？（手机 + 电脑）
- 长期维护意愿（会不会 2 个月后就不记了？）

**常见 AI 失败模式**：
- 马上说“用 Notion 做个数据库”或“用飞书多维表格”
- 设计复杂的分类体系（餐饮/交通/娱乐...）
- 推荐各种记账 App（随手记、MoneyWiz 等）

**成功标准**：
- 挑战“一定要做 App”这个假设
- 至少提出“先在现有 Excel 里加一个简单模板”的 processize 路径
- 发现用户对“分类”的真实痛点（不是不想分，是分得太细烦）

---

### 场景 C3: “给我的小手作店做一个网站”

**初始用户输入**：
> 我在做一些手作的东西（针织、陶艺），想做一个简单的网站，把作品放上去，别人能看到、能联系我买。不要太花哨，就清爽一点就行。

**用户真实背景**：
- 现在在小红书 + 朋友圈卖
- 偶尔有人问价格、问能不能定制
- 想有自己的“门面”
- 完全不会前端，也不想学
- 预算 500-1000 元以内
- 希望“放上去就不用管了”，但其实每个月都会上新
- 担心收款、发货、客服这些事

**关键测试点**：
- 真正的问题是“展示”还是“交易”还是“客服”？
- 现有 workaround（小红书）的优势和不足
- 更新频率 vs “放上去就不管”的矛盾
- 技术能力为零 + 预算有限 → 几乎必然走 no-code / 模板路线
- 长期维护能力（每月上新是谁在做？）

**常见 AI 失败模式**：
- 推荐 Next.js + Vercel + Stripe 一条龙
- 假设用户会自己维护内容
- 忽略“交易”和“客服”其实是更大的痛

**成功标准**：
- 把需求拆成“展示 + 咨询 + 下单 + 售后”几个子问题
- 明确指出用户当前最缺的可能是“稳定的收款和沟通通道”，而不是漂亮网站
- 推荐路径中必须包含 no-code 选项 + 手动 processize 选项

---

### 场景 C4: “健身打卡 + 看进步”

**初始用户输入**：
> 我想做一个 App，记录我健身，打卡，然后能看到自己的进步曲线。就是那种能激励我的那种。

**用户真实背景**：
- 现在用手机备忘录记“今天练了什么 + 重量”
- 偶尔用 Excel 画个表看趋势
- 真正的问题是“坚持不下去”
- 用户是 28 岁程序员，技术能力很强，但对自己的执行力没信心
- 讨厌复杂的功能（“我不要那种要我输入一堆数据的”）

**关键测试点**：
- 痛点的根源是“记录麻烦”还是“缺乏外部激励”还是“不知道怎么坚持”？
- 用户技术能力强 → 可以用更激进的技术方案
- 但“坚持”问题可能不是技术能解决的（需要社交？打赌？教练？）
- 进步曲线到底要展示什么？（重量？围度？照片？感受？）

**常见 AI 失败模式**：
- 直接开始设计漂亮的打卡 UI + 图表
- 推荐 Hevy / Strong 等现成 App（用户可能已经试过）
- 完全不问“记录本身是不是你坚持不下去的主要原因”

**成功标准**：
- 至少把“记录”问题和“坚持”问题拆开讨论
- 发现用户其实更需要的是“外部问责机制”而不是更好的记录工具
- 在 DecisionPoint 中讨论“是否需要社交功能”时有真实权衡

---

### 场景 C5: “家庭相册共享，但不想用微信”

**初始用户输入**：
> 我想做一个家庭相册共享的东西。就是把家里人的照片、视频放到一个地方，大家都能看到和下载。不要用微信，因为微信空间有限，也不够整齐。

**用户真实背景**：
- 家里有老人 + 小孩 + 自己
- 老人不会用复杂的东西
- 现在靠微信群发，找历史照片很麻烦
- 担心隐私（不想让所有照片都在腾讯服务器）
- 用户自己是 IT 从业者，但家里其他人不是
- 希望“发一次就能永久保存”

**关键测试点**：
- 技术能力不对称（用户强，真正用户弱）
- 隐私 vs 便利的真实权衡
- 老人能否/愿否使用新 App
- “永久保存” vs 实际存储成本
- 上传便利性（手机直接传 vs 要转存）

**常见 AI 失败模式**：
- 推荐自建 Nextcloud / Immich（完全不考虑老人使用门槛）
- 推荐 Google Photos / iCloud（忽略隐私诉求）
- 假设所有家庭成员技术水平一样

**成功标准**：
- 明确识别出“使用门槛必须极低（接近微信）”这个硬约束
- 在隐私和便利之间做出有依据的选择或列出清晰权衡
- 至少提出一个“混合方案”（例如核心照片用本地 NAS + 老人只看精选）

---

### 场景 C6: “我有一个小说/故事的想法，想做成游戏”

**初始用户输入**：
> 我脑子里有一个故事，想把它做成一个像《原神》或者文字冒险游戏的东西。就是玩家可以选择不同的路线，最后有不同结局。

**用户真实背景**：
- 用户是 24 岁文科生，写过一些短篇
- 完全不会编程，也不会画画、不会做音乐
- 预算为零
- 真正驱动的是“想把这个故事讲出来，让别人体验”
- 对“做游戏”的理解停留在“选分支 + 看结局”

**关键测试点**：
- “做游戏” vs “讲故事”的本质区别
- 完全零技术 + 零美术 + 零预算 → 几乎所有技术路线都被剪掉
- 交互复杂度 vs 作者维护能力
- 发布和分发问题（Steam？ itch.io？微信小程序？）
- 可能最好的路径其实是“互动小说”而不是“游戏”

**常见 AI 失败模式**：
- 推荐 Unity / Godot + 学 C# / GDScript
- 推荐 Ren'Py（虽然 Ren'Py 其实不错，但用户完全不知道要学什么）
- 直接开始设计系统、存档、成就等

**成功标准**：
- 强烈挑战“一定要做成可交互游戏”这个假设
- 至少提出 2-3 个极低门槛的替代形式（互动小说网页、Twine、甚至纯文字 + 插画 PDF）
- 明确写出“如果你真的只想讲这个故事，目前最现实的路径是 XXX”
- 把美术、音乐、编程这三个几乎不可能的门槛都显性化

## 3. 压力场景使用方式（给未来测试者）

### 3.1 RED 阶段（无 skill 时）

1. 把场景的“初始用户输入”直接喂给一个干净的 agent（没有任何 vibe-unpack 相关指导）。
2. 观察并记录：
   - 它是否立刻给技术方案？
   - 是否问了足够多关于约束的问题？
   - 是否把“像小红书”当真去实现了？
   - 输出的需求规格是否结构化、可消费？
3. 记录具体的失败表现（原话 + 行为）。

### 3.2 GREEN 阶段（有 skill 时）

1. 同样输入喂给加载了 `vibe-unpack` 的 agent。
2. 要求它输出：
   - `demand-spec.md`（按阶段 A 格式）
   - `demand-graph.json`（按阶段 B schema）
3. 检查是否满足该场景的“成功标准”。
4. 检查是否**没有**触碰 Out-of-Scope 内容（技术推荐、技能匹配等）。

### 3.3 迭代信号

如果在某个场景上反复失败，说明：
- 某个维度的问题簇不够强
- 闭合条件太松
- 原则描述不够清晰（agent 还是忍不住推荐技术）

## 4. 场景覆盖矩阵（用于后续完整性检查）

| 场景 | 模糊度 | 技术背景 | 维护意愿 | 多人需求 | 预算 | 核心风险类型 |
|------|--------|----------|----------|----------|------|--------------|
| C1 孩子日常 | 极高 | 零 | 低 | 是（家人） | 极低 | 长期性 + 能力 |
| C2 记账 | 中 | 中（Excel） | 中低 | 否 | 低 | 过度工程化 |
| C3 手作店 | 高 | 零 | 中 | 客户 | 低 | 更新 vs 维护 |
| C4 健身 | 中 | 高 | 低（执行力） | 可选 | 中 | 技术解决不了的问题 |
| C5 家庭相册 | 高 | 不对称 | 中 | 是（全家） | 中 | 使用门槛 + 隐私 |
| C6 小说游戏 | 极高 | 零 | 未知 | 玩家 | 零 | 野心与能力完全不匹配 |

这个矩阵可以用来检查未来测试是否覆盖了足够多样的约束组合。

## 6. 整体设计阶段总结（A+B+C）

至此，`vibe-unpack` 的设计基线已完成：

- **阶段 A**：核心定位、8 条铁律、严格 In/Out 边界、双格式输出合同
- **阶段 B**：节点/关系 schema、六大展开维度、闭合条件、决策建模方式
- **阶段 C**：6 个可执行的压力场景 + TDD 验证方法

**下一步实际工作建议**：
1. 基于 A+B+C 撰写 `vibe-unpack/SKILL.md`（核心逻辑、追问流程、输出模板）
2. 实现必要的辅助工具（例如生成 demand-graph.json 的小脚本，或 Mermaid 可视化模板）
3. 按场景 C1-C6 进行实际 RED → GREEN → 迭代循环
4. 只有通过了至少 4 个压力场景的严格测试，才认为 skill 可用
